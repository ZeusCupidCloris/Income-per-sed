# 年度内置日历替换

每年手动更新网页与小组件的内置数据，继续使用现有单文件交付。本文是下一年度（2027 年）的操作清单，不包含推测的节假日日期，也不表示已经核实该年度公告或完成更新；当前交付仍使用 2026 年数据。不增加在线同步或日历备份功能。

## 先确认正式来源

- [ ] 在中国政府网核对国务院办公厅正式年度节假日安排，记录公告标题、原文地址、公布日期及有无后续更正。转载或搜索摘要只作查找线索。
- [ ] 从原文逐项整理全部放假日期与调休上班日期。连续假期展开为每天的 `YYYY-MM-DD`，包含假期中的周末；普通周末由既有周末规则处理。
- [ ] 核对每个日期真实存在、属于目标覆盖范围、没有重复、没有同时出现在放假和调休上班两组。
- [ ] 单独核对跨年假期涉及的边界日期，明确新包覆盖起止范围，以及旧年份回溯在范围外使用的既有规则，不把旧年日期改写成新年。
- [ ] 根据正式日期表独立核算每月工作日及全年合计，作为计算核对依据。

目标年度、公告原文、数据版本、录入日期和核对结果写入本次交付记录。来源尚不能确认时停留在清单准备阶段，不修改内置日期。

## 同步位置

先编辑 [Develop](../Income-per-sed-Develop.html) 与 [小组件](../IncomeWidget.js)，Push 始终由 Develop 生成。

| 文件与位置 | 需要核对的内容 |
| --- | --- |
| Develop `APP_RELEASE.calendarVersion` | 使用目标年度数据版本，例如 `cn-mainland-2027-v1`；同年更正递增数据修订号 |
| Develop `DEFAULT_CONFIG.calendarCoverage` | `start`、`end`、`label`、`version`、`timeZone`、`generatedAt` 和 `source`；录入日期与公告日期分别记录，时区沿用 `Asia/Shanghai` |
| Develop `DEFAULT_CONFIG.holidays` / `specialWorkdays` | 正式日期表对应的两组完整列表，按日期排序 |
| Develop `APP_RELEASE.calendarChecksum` | 用既有 `CalendarManifest` 算法重算内置指纹，并确认诊断中的 `valid` 为真 |
| Widget `APP.calendarCoverage` | 起止日期与版本同网页，`APP.timeZone` 保持一致 |
| Widget `HOLIDAYS` / `SPECIAL_WORKDAYS` | 与网页的两组日期集合完全一致 |
| Word 使用手册 | 适用年度、日历来源、年度替换步骤、覆盖范围外说明及受影响图片 |
| 发布清单及其他三文件 | 按[四文件同步规则](REPOSITORY_POLICY.md#文件截图和说明书同步)统一产品版本、交付编号、内容说明与校验值 |

`CalendarManifest` 的指纹材料是覆盖范围的 `start`、`end`、`version`、`timeZone`，加上 `specialWorkdays` 与 `holidays` 两个数组；使用现有 `TransactionalStorage.stableSerialize` 和 `checksumText`，不另造算法。数组顺序参与指纹，因此先排序再计算。

`release:prepare` 负责生成 Push 和更新手册中的源文件哈希，**不会自动录入新年日历、重算日历指纹或改写说明书功能文字**。这些内容必须先完成核对。

用户设置中的 `annualWorkDays` 与内置日历不是同一项。核对默认值及说明是否仍适用，同时保留用户已有工资、作息和全年工作日配置；不要在更换内置日历时静默覆盖用户设置。

## 核对实际生效的数据

- [ ] 在隔离的浏览器配置中打开新 Develop，确认无导入数据时采用新内置日历，覆盖日期、版本和指纹一致。
- [ ] 核对已有配置的升级路径。网页 `CalendarDataStore.load()` 会优先读取已导入日历；替换 HTML 不会自动删除该数据。说明书应告知如何识别当前来源，并由用户选择是否使用现有“恢复内置”入口，不清空整份本地存储。
- [ ] 在 Scriptable 手动运行新脚本，核对新覆盖年份及设置仍被保留；更新网页日历不会自动改写脚本中的日期集合。
- [ ] 超出声明覆盖范围时，提示和降级行为仍清楚，不把未覆盖年份宣称为已含正式节假日安排。

## 验收顺序

先用新年份代表日期检查计算：普通工作日、普通周末、调休周末、法定假期、月末、跨月与跨年边界；工作日覆盖上班前、上午、午休、下午与下班后三种计薪口径。每月工作日合计与前面的人工核算表对照。

年度替换时逐项核对以下固定日期，而不是全局替换年份：

- `tests/widget-parity.spec.js` 的计算示例包含写死的 2026 年日期，需要更新目标年度代表案例。
- Develop 的 `runBoundaryRegressionChecks()` 包含“2026-01-01 已覆盖、2027-01-01 未覆盖”的断言，需与新的覆盖起止范围一致；相邻的节假日、调休工作日、普通工作日及跨午夜/年末状态案例，也需依据新年度正式日历核对。该检查由 `tests/input-device-motion.spec.js` 调用，属于完整 Edge 验收，不可只更新小组件对照测试。
- 仅验证日期运算的月末、年末和闰日案例可以保留固定年份；涉及日历覆盖或工作状态的旧日期若继续保留，明确其验证的是旧覆盖范围或范围外行为，不把旧用例通过当作新年度正确的证明。

先运行已有计算专项：

```powershell
npm.cmd run check:focus -- --group data --browser edge
```

`widget-parity.spec.js` 对照两端节假日与调休集合、检查日期有效性、网页覆盖范围内日期及两组冲突，并核对收入计算和金额格式。小组件以 `Set` 保存日期，原始重复项会被去重，因此仍需人工检查原始列表；两端覆盖元数据也需按上表分别核对。两端一致不等于与官方公告一致。

年度日历改动影响共享计算。四文件内容准备完成后，按现有分流执行**完整验收**；本次仅维护这份清单时只检查文档。入口与写入范围统一见[脚本索引](../Attachment/scripts-index.md#三个主要入口)。

## 四文件交付

1. 按维护策略递增统一产品版本和交付编号，并完成 Word 的年度说明与受影响截图。没有功能变化的组件保留既有行为，同时核对适用说明及统一版本。
2. 执行 `npm run release:prepare` 生成 Push、同步手册书签校验值及外部清单；检查生成结果与 Word 排版。
3. 按既有流程核对 README 图片来源，执行 `npm run release:repeatability`，完成完整验收。
4. 将四文件、发布清单与验收记录一起提交 PR。检查通过后合并，验证 Pages 与本次 Push 字节一致，再核对桌面和交付包。
5. 将自动检查、桌面观察、用户实机反馈分别记录。尚在观察中的项目保留“持续观察中，暂未发现问题”，不提前改成最终通过。普通年度维护不创建 GitHub Release。

小组件测试以 Intl 模拟 Scriptable 日期格式化接口，不代表真实 iPhone/iPad 渲染或系统刷新验收。
