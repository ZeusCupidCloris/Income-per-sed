## 原始问题定位

原失败位于 `long-amount-layout.spec.js` 的 Develop、390 像素、浅色压力场景。该场景同时使用超长金额、回溯、主题过渡及视口变更，发生在原专项第 50 项。轨迹显示恢复 390 像素视口的调用完成后，后续写入诊断阶段标记的 `page.evaluate` 收到页面进程崩溃响应；不是金额溢出或单元格边界断言失败，也没有证据表明那个简单标记赋值是根因。

对原时间段的 Windows Application 1000、1001 事件查询没有找到匹配记录，没有取得可用于归因的原生堆栈。这个空结果不能排除原生或资源问题，也不能用它证明应用没有影响。

## 原生记录与内存观察

本机记录的环境为 Playwright 1.62.1、Windows WebKit revision 2336、浏览器版本 26.5，原生程序为 64 位。依赖和浏览器二进制均未替换。

连续检查使用一个原生浏览器外壳进程，期间多次创建不同的 Web 页面进程。因此不能把浏览器会话复用理解成同一个 JavaScript 堆一直累计。有效旁路内存记录覆盖本轮末段约四分钟，共 109 条有进程匹配的数据，包含 22 个不同的 Web 页面进程；这不是全程内存曲线。

该段中三个原生进程的私有字节之和峰值约 932 MiB，单个 Web 页面进程峰值约 448 MiB。这些是进程指标，不是 JavaScript 堆大小或物理内存用量；没有原崩溃当时的同类数据，不能据此判断内存泄漏、内存不足或已经排除这些因素。

最初的 Windows PowerShell 采样器发生数组类型兼容问题，只有空进程匹配，未记为有效采样。保留原文件，在 PowerShell 7 中另存修正后的观察；没有重启正在执行的浏览器会话来获取更好看的结果。

补充日志的方法参考 [Playwright 原生日志说明](https://playwright.dev/docs/ci#debugging-browser-launches)，使用 `DEBUG=pw:browser` 采集进程启动与退出。检索到的[同 revision Linux 长运行崩溃报告](https://github.com/microsoft/playwright/issues/42330)和[Linux 网络进程库报告](https://github.com/microsoft/playwright/issues/42803)条件与本机 Windows 不同，未将其套作本案根因或升级依据。
