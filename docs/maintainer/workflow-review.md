# 工作流重复检查评估

核查基线：2026-09-30。本页是方案，不修改工作流、合并保护或权限；再次实施前核对当时配置。

## 文件位置与冗余核查

- 本轮按全文件用途表核对交付、工具、配置、角色文档、图片及历史证据，新增资料也必须登记并通过内部链接检查。
- 三份跨角色索引迁入 `Attachment`，不保留 docs、scripts、tests 下的旧索引副本；这是迁移，不是删除历史证据。
- 四份交付与清单保留既有位置；角色入口仍在 docs，自动工具仍按 scripts/tests/config/.github 归类，图片与视觉测试基线不互相替代。
- 对迁移前仍存在的 Git 管理文件做 SHA-256 重复组检查，未发现字节完全相同的文件组。没有足够证据把其他文件判定为无用，因此不为减少文件数量而额外删除。
- 这是仓库内文件核查，不清理电脑桌面、下载目录或仓库外备份。后续相似内容需要人工核对用途，不能仅凭哈希不同或无链接决定删除。

## 阶段职责对照

| 阶段 | 检查内容 | 结论 |
| --- | --- | --- |
| PR Quality | 交付/组件测试、生成一致性、图片与索引；Edge 全量；WebKit 专项 | 必须保留，合并前发现问题 |
| main Quality | 同一套三项检查，全部成功后调用 Pages | 保留，验证实际合并结果，不等于 PR 分支提交 |
| Pages | 在同一提交重新生成交付、确认无差异，然后部署 Push 并核验线上字节 | 部署与线上核验必须保留；重复构建可评估 |
| Release 标签校验 | 交付测试、标签分类、main 归属、带标签构建、图片索引与 Edge | 大版本正式产物的独立防线，不能仅因 main 曾通过就删除 |
| Release 发布 | 分类后上传已验证附件 | 发布职责，不是重复测试 |

Quality 的三项任务分别在独立环境执行，重复安装依赖是任务隔离，不是重复验收。Pages 只有 main 三项成功才运行，不存在另一条独立 push 部署链。

## 可精简候选及风险

1. **Pages 重复生成交付**：Quality 的交付检查已在同一 main SHA 完成一次。可在单独 PR 研究改为只读交付校验，仍保留 `git diff` 和线上字节核验。收益主要是减少生成工具对部署的耦合，当前快任务本身节省有限。
2. **Quality 与 Pages 重复准备运行环境**：任务隔离保证部署权限不进入测试任务。不要为减少安装而合并权限；现有 npm 缓存保留即可。
3. **PR 与 main 双跑**：不能直接取消 main 完整检查。以后若复用证据，必须绑定精确提交、工具版本、成功结论和产物摘要，不能只按分支名认定通过；目前复杂度大于收益。
4. **Release 重跑 Edge**：仅在经确认的大版本运行，频率低。建议保留，避免标签与交付来源不符。现有 Release 未单独重跑 WebKit/组件测试，依赖 main 的验收；这是覆盖边界，不是可以删除的冗余。

## 建议决策

本轮不删除任何质量关卡。下一轮只评估第一项，比较实际耗时和失败诊断，再决定是否实施。稳定保留三项 main 必需检查及 Pages 内容核验。

大版本发布前需单独落实 [V3/V4/V5 展示名称及授权规则](../REPOSITORY_POLICY.md#当前发布约定)：当前工作流仍兼容 `v*` 标签和旧标题格式，文档约定不是自动执行限制。本轮不触发 Release。
