## 风险与后续

[原 WebKit 偶发页面目标崩溃](webkit-stability.md)在本轮重现，根因仍未确认。新旧两次失败均为 Develop、390 像素、浅色起始的长金额回溯/主题/缩放压力用例；恢复 390 像素视口的协议调用已经完成，随后测试第 153 行写入阶段标记时收到 `Target crashed`。轨迹里的测试步骤与协议层各有一条错误记录，对应同一次用例失败，不算两次独立崩溃。没有证据说明那个标记赋值本身是根因。

新旧原始轨迹、首次日志均保留，没有重新运行失败用例。失败后为后续用例启动新工作进程不等于重试失败用例。当前测试服务实际返回的 Develop、Push 与候选字节相同；崩溃时间窗口内的 Windows Application 1000/1001 查询没有记录，也未找到相应转储，未取得原生堆栈。驱动主进程在清理时退出码为零，不能据此排除子页面目标问题；空事件结果也不能排除应用、原生或资源原因。

旧基准已经有相同症状，因此不能直接断言是这十二处定义删除新引入，也不能据此排除它对发生概率的影响。没有为获得通过而关闭动画、改布局阈值、换驱动或升级依赖。本轮不把静态精简和未知原因的崩溃修复混为一件事。

另外两项超时发生在 `release-behavior.spec.js:106`，等待刷新后重新打开的收入面板就绪。两份轨迹均已进入第三种固定日薪模式；最后一次点击前，从创建页面算起已经分别经过约 44.08 秒、43.86 秒，而整个测试只有 45 秒预算，并非单独等待面板 45 秒。最终错误快照中面板已打开，日薪输入值为 `2600.00`，时薪为 `400.00`。这些证据不支持把失败直接写成工资保存丢失，但最后的值断言尚未完成，因此两项仍记失败；总预算耗尽或交接余量不足只是待验证解释，没有扩大超时或重跑来消除失败。

下一步先按工资模式拆分持久化检查，保留原断言、每例 45 秒上限及必要的跨模式覆盖，区分测试总预算与真实交接问题。同时建立缩放失败的最小复现，分别控制长金额、主题过渡、返回实时和视口变化，取得可归因的原生或渲染证据。当前不开展下一批删除或发布；稳定性问题定位后，再只读审计选择器与关键帧的实际使用关系，算法改动继续以采样为依据。
